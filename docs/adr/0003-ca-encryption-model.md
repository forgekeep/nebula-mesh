# ADR 0003 — CA key encryption model: operator-derived KEK vs status quo

- **Status**: Accepted (2026-05-13)
- **Extends**: [ADR 0002](0002-per-operator-cas.md) (per-operator CAs, server-master-key envelope encryption)
- **Tracking issue**: [#68](https://github.com/forgekeep/nebula-mesh/issues/68)

## 1. Context

[ADR 0002](0002-per-operator-cas.md) §4.4 fixed the per-CA encryption posture: each CA's PKCS#8 private key is sealed under a per-CA AES-256-GCM data-encryption key (DEK); the DEK is wrapped under a process-wide master KEK that the operator supplies through `NEBULA_MGMT_MASTER_KEY`. The accepted threat model explicitly states that **DB + master key ⇒ all CAs**: any actor with shell access to the running server can decrypt every CA on the box.

Issue [#68](https://github.com/forgekeep/nebula-mesh/issues/68) (follow-up to [#31](https://github.com/forgekeep/nebula-mesh/issues/31)) asks the obvious next question: should CA encryption be bound to **the owning operator's credentials**, so that even a server administrator with full shell + DB access cannot decrypt another operator's CA without that operator's cooperation? This is the "zero-knowledge" framing from the #31 discussion.

The question is not trivial because the current product **signs certificates unattended**:

- Agent enrollment (`POST /api/v1/enroll`) — the operator who owns the CA is rarely online when a fresh host bootstraps.
- Cert auto-rotation — when the agent polls within the renewal window, the server signs a new cert in the same response (`internal/api/updates.go:63-87`). No operator session is involved.

Any scheme that requires the operator's password material at sign time **breaks both flows** unless it caches an unwrap KEK in memory for the duration of the operator's session. That cache is itself a security regression compared to the status quo (a long-lived unwrap key in RAM survives the operator logging out and is readable by anyone who can read the process's memory, e.g. `root`).

This ADR records the trade-off explicitly and chooses a path. **Implementation is out of scope**; if a non-status-quo option is picked, it is tracked in a follow-up issue.

## 2. Current state (the status quo, summarised)

- `internal/keystore/keystore.go` exposes `Master` with `MasterKeySize = 32`, generated by the operator out-of-band, supplied at startup, **never persisted**.
- `Master.GenerateDEK()` produces a per-CA DEK; `WrapDEK / UnwrapDEK` envelope it; `WrapBlob / UnwrapBlob` seal the PKCS#8 under the DEK. AES-256-GCM throughout.
- `internal/auth/password.go` hashes operator passwords with bcrypt. There is **no Argon2id / scrypt / PBKDF2** in the codebase today — adding operator-derived key material is itself new dependency / new code.
- Operators may authenticate via password+TOTP **or** via OIDC. OIDC operators have **no local password** — there is nothing to derive a KEK from on the server.

## 3. Forces

- **A. Tenancy promise.** ADR 0002 enables per-operator CAs but does not give each operator cryptographic privacy from the server admin. If the project's positioning is "self-hosted, multi-operator, isolated CAs", we should at least name how far the isolation goes.
- **B. Unattended signing is a feature.** Background cert auto-rotation is one of nebula-mesh's selling points (`README.md`: "atomic writes ... auto-rotation"). Any scheme that requires operator presence at sign time changes the product.
- **C. OIDC interop.** OIDC operators are first-class citizens (`internal/web/oidc.go`). Schemes that depend on a local password lock OIDC operators out — or fall back to a server-side KEK for them, undermining the very claim the scheme is sold on.
- **D. Recovery cost.** Password reset must not brick CAs. Today bcrypt rehashes leave the CA blob untouched; any operator-derived KEK must come with a documented recovery story (recovery codes, admin override, or accepted loss).
- **E. Compromise scope.** Status quo (Option A) gives root-on-server access to every CA; the alternatives narrow the scope but only at the cost of (B), (C), or (D). The honest answer is that on a single-binary self-hosted box, the server admin **is** the trust root for the control plane regardless of where the keys live — there is no separation of root duties on a $5 VM.
- **F. KMS deferral (ADR 0002 §3D).** True separation of server-admin from CA-signing belongs in an external signer (KMS / HSM), which ADR 0002 already lists as out of scope for the single-binary deployment story.

## 4. Options

### A. Status quo — server master key only

Envelope encryption with `NEBULA_MGMT_MASTER_KEY`. The decrypted PKCS#8 reaches the signing closure for ~milliseconds and is zeroised after use (`internal/keystore/keystore.go`).

- **Threat model.**
  - DB read: useless (CA blobs are AEAD-sealed under DEKs, DEKs are AEAD-sealed under the master key).
  - DB + master key: all CAs.
  - DB + server root + readable RAM: all CAs (the master key is in process memory while the server runs).
  - Operator password compromise: no impact (passwords don't participate in CA encryption).
  - Recovery code compromise: no impact.
- **Impact on flows.**
  - Enrollment: unchanged (server signs on demand).
  - Auto-rotation: unchanged.
  - Password reset: trivial, doesn't touch CAs.
  - OIDC: trivial, doesn't touch CAs.
  - 2FA: trivial.
  - Backups: one file (DB); the master key stays in the operator's secret manager.
- **Cost.** Zero. This is what we ship.

### B. Hybrid — DEK wrapped under both server master key *and* operator-derived KEK

For each CA, store **two** wrapped copies of the DEK:

- `encrypted_key_dek_master` — DEK sealed under `NEBULA_MGMT_MASTER_KEY` (for unattended signing).
- `encrypted_key_dek_operator` — DEK sealed under `Argon2id(password, salt, params)` of the owning operator's password at the moment that password is set (for operator-initiated export / manual re-key / recovery).

At sign time the server still unwraps via the master path; the operator KEK is exercised only on explicit "export this CA" / "re-key under my new password" / "rotate operator KEK" actions.

- **Threat model.**
  - DB read: useless.
  - DB + master key: all CAs (same as A; the second wrap is additive, not protective).
  - DB + server root + RAM: all CAs (same as A).
  - DB + operator password (no master key): one CA per compromised operator. Strictly **stronger** than status quo for the "stolen-backup + leaked-operator-password" attacker who does not have shell on the running server.
  - Recovery code compromise: depends on whether recovery codes participate (see below).
- **Impact on flows.**
  - Enrollment: unchanged (server still signs via the master path).
  - Auto-rotation: unchanged.
  - Password reset: **must re-wrap the operator copy** under the KEK derived from the new password. With current bcrypt code this means: at password set, hold the plaintext briefly, derive the operator KEK with Argon2id, rewrap, drop the plaintext. Recovery code holds a backup wrap, same dance.
  - OIDC: operator copy not derivable — store **only** the master wrap for OIDC operators, document the asymmetry. Effectively reverts to Option A for OIDC owners.
  - 2FA / TOTP: orthogonal (TOTP is a second factor for sign-in, not a key derivation source; it would only help if we also bound a KEK to the TOTP secret, which is fragile because TOTP secrets are stored server-side anyway).
  - Backups: same one file. The operator-wrap copy exists in the DB; recovery from a backup requires either the master key (same as A) or the operator's password (new path).
- **Cost.** Medium. New Argon2id helper, password-set / password-reset / recovery-code-redemption all become CA-touching operations (today they touch only the operator row). Migration for existing CAs: backfill the operator wrap at the next successful operator login (we have the password in cleartext briefly there). OIDC operators do not get the operator wrap; document the gap.

### C. Zero-knowledge — DEK wrapped *only* under operator-derived KEK

No master-key path. The server cannot decrypt a CA without the owning operator's cooperation.

- **Threat model.**
  - DB read: useless.
  - DB + server root: useless without operator participation. **This is the change.**
  - DB + operator password: that operator's CA.
  - Recovery code compromise: that operator's CA (if recovery codes hold a backup wrap).
- **Impact on flows.**
  - **Enrollment is broken.** The server cannot mint a host certificate without unwrapping the CA private key, which requires the operator's password at that moment. Mitigations:
    - **C1: unlock cache.** When the operator logs in, derive the KEK with Argon2id, hold it in process memory until the operator's session ends. While the cache is hot, signing works; when it cools, enrollment requests for hosts owned by that operator fail with a documented `503 ca_locked`. This **destroys the zero-knowledge property** the moment any operator logs in — root-on-server can read the cache from RAM. The cache also leaks across operator restarts of the server: a long-lived cache is exactly what an attacker steals.
    - **C2: pre-sign blanks.** Operator-blessed batches of pre-signed certificates with placeholder identities, redeemed at enroll time. Impractical for IP allocation, blocklist correlation, audit trail.
    - **C3: per-host operator ceremony.** Operator unlocks the CA explicitly each time a host enrols. Doesn't scale beyond demo.
  - **Auto-rotation is broken** for the same reason as enrollment, modulo the same C1/C2/C3 mitigations.
  - Password reset: **bricks all CAs** the operator owns unless a recovery-code backup wrap exists. With recovery code: same dance as B, doubled. Without: operator loses every CA on password reset.
  - OIDC: **no password to derive from**. Either OIDC operators cannot own CAs at all, or a server-side KEK is reintroduced for them — which collapses C back into A for those operators.
  - 2FA / TOTP: same as B — TOTP secrets are server-stored, so binding them to the KEK gives no extra security against root-on-server.
  - Backups: one file. But the backup is **only useful** if the operator's password (or a recovery code) survived alongside it. Lose the operator's secrets, lose the CAs. Document loudly.
- **Cost.** High. Cache state machine, `ca_locked` HTTP status handling, agent-side handling for delayed signing, operator session lifecycle hooks, recovery-code-driven backup wraps, OIDC carve-outs. The asymmetry between local and OIDC operators is the most awkward part: the headline property ("the server cannot decrypt your CA") does not hold uniformly.

### D. KMS / HSM signing — deferred

Same as ADR 0002 §3D. A `pki.Signer` interface fronts a remote signer; the CA private key never lives in nebula-mesh memory. Out of scope for the single-binary deployment story per ADR 0002 §3D. **Re-listed here as still deferred**; pursue when the project starts to ship a multi-tier deployment story.

## 5. Comparison summary

| | A: server master | B: hybrid | C: zero-knowledge | D: KMS (deferred) |
|---|---|---|---|---|
| DB-only theft | safe | safe | safe | safe |
| DB + master key | all CAs | all CAs | n/a | n/a |
| DB + server root | all CAs | all CAs | safe **iff** no operator was recently online | safe |
| DB + operator password | safe | one CA | one CA | safe |
| Unattended enrollment | ✅ | ✅ | ❌ (or eroded via cache) | ✅ |
| Unattended cert rotation | ✅ | ✅ | ❌ (or eroded via cache) | ✅ |
| OIDC owners | ✅ | mixed (master wrap only) | ❌ or mixed | ✅ |
| Password reset | trivial | re-wrap operator copy | bricks CAs without recovery | trivial |
| Backup story | DB + master key in vault | DB + master key (+ operator password as extra path) | DB + operator password / recovery codes | DB + KMS access |
| Implementation cost | 0 | medium | high | very high (out of scope) |
| Eliminates root-on-server risk | no | no | partially (until first login) | yes |

## 6. Decision

**Stay on Option A (status quo) and document the posture explicitly.** Plan to revisit when the project ships an external signer (Option D).

### Reasoning

1. **The "zero-knowledge" property Option C promises is undeliverable on the deployment story we ship.** On a single $5 VM where the operator *is* the server admin, server-root and operator-credential are the same human. The C1 unlock cache reintroduces the attacker we wanted to lock out, the moment any signing happens. Options C2 / C3 do not scale to even small fleets. The headline ("the server can't read your CA") is true only between operator logins; for the use cases this project targets, that window is short. We do not want to sell a property we cannot uphold.

2. **Option B provides the *backup* protection that has actual real-world value — at meaningful implementation cost — without breaking unattended signing.** A leaked DB *backup* is a far more realistic attacker than a leaked DB *plus* a leaked master key, and Option B forces that attacker to compromise *one* operator's password to read *one* CA. That is a measurable improvement. We hold this option in reserve and revisit when:
   - OIDC-only operator support is downgraded to "rare", and / or
   - A clear customer ask shows up for backup-leak protection, and / or
   - The Argon2id helper lands for another reason (e.g. encrypted exports).

3. **Option D — KMS / external signer — is the right long-term answer.** It solves the root-on-server problem without the C-class flow disruption, and it cleanly subsumes Option B. The `pki.Signer` seam contemplated in ADR 0001 §7 / ADR 0002 §3D / §F is the migration path. When that ADR lands, this ADR's decision can be revisited at no schema cost (Option C-style guarantees become deliverable through a KMS that the operator controls; nebula-mesh never sees the key).

4. **The status quo is **already** the threat model documented in ADR 0002 §4.4 and in the README's "Backups & key handling" section.** Choosing A means we change no code, we make the property an explicit, named decision in the architecture record, and we name the alternatives so future contributors stop having to rediscover the analysis.

### Migration from current state

None. Option A *is* the current state.

### Reversibility

The choice is reversible at the schema level: ADR 0002's `encrypted_key_dek` column already isolates the wrapping algorithm from everything else. Moving to Option B is an additive migration (add `encrypted_key_dek_operator NULL`, populate at next operator login). Moving to Option D is the `pki.Signer` interface swap.

The choice is **per-CA-reversible** in principle: a future hybrid could let each operator choose Option A or Option B at CA creation. We do not commit to that flexibility today (single mode per server is simpler to reason about).

## 7. Consequences

- ADR 0002 stands as written; this ADR extends it without superseding.
- The README and `docs/server.md` should add one sentence near the master-key documentation that names ADR 0003: "The server admin can decrypt every CA on the box. We accept this for the single-binary deployment; see ADR 0003 for the alternatives and why we did not adopt them."
- No new code, no new migrations, no new env vars.
- A future "external signer" ADR (KMS / HSM, ADR 0004 territory? — separate doc) is unblocked.

## 8. Out of scope

- Implementing Options B, C, or D. Each requires its own ADR + implementation issue.
- Operator-owned export-only KEKs (a degenerate case of B used purely for offline export of a CA bundle).
- Per-CA mode selection (status quo vs hybrid). If we ever pursue this, it's a new ADR.
